# Практическая работа — Модуль 03

**Тема:** Внедрение зависимостей (Dependency Injection. Логирование)
**Проект:** `ProductsApi` (Product)
**Используемые технологии:** Visual Studio 2022+, C#, ASP.NET Core Web API, .NET 8 (LTS), Swagger/OpenAPI. База данных не используется — данные хранятся в памяти приложения.

## Как запустить

```bash
cd prac
dotnet run
```

Откройте Swagger UI по адресу из вывода консоли.

## Что реализовано

Методичка проведена пошагово: сначала сервис создаётся напрямую в контроллере через `new ProductService()` (шаг 5), затем эта прямая связь убирается в пользу интерфейса `IProductService` без регистрации в DI-контейнере — на этом шаге приложение падает при обращении к контроллеру, поскольку ASP.NET Core не может подобрать реализацию для интерфейса (шаг 6), и только после регистрации `AddScoped<IProductService, ProductService>()` в `Program.cs` контроллер снова создаётся исправно (шаг 7). В финальном коде в этой папке зафиксирован только итоговый, корректный вариант — с DI через конструктор.

| Метод | Endpoint | Назначение | Успешный код | Код ошибки |
|---|---|---|---|---|
| GET | `/api/products` | получить список всех товаров | 200 OK | — |
| GET | `/api/products/{id}` | получить товар по Id | 200 OK | 404 Not Found |

Логирование в `ProductsController`:

- `LogInformation` — при запросе списка товаров и при успешном поиске товара по Id;
- `LogWarning` — если товар с указанным Id не найден.

Шаг 13 методички (временное добавление `LogTrace`/`LogDebug`/…/`LogCritical` и смена `Logging:LogLevel:Default` в `appsettings.json` с `Information` на `Warning`) — учебное упражнение по наблюдению за уровнями логирования, в финальный код не включено; см. ответ на вопрос ниже.

## Ответ на вопрос из методички

**Почему сообщения Information больше не отображаются, а Warning и Error продолжают отображаться, после смены `Logging:LogLevel:Default` с `Information` на `Warning`?**

Уровни логирования в ASP.NET Core образуют иерархию по возрастанию серьёзности: `Trace < Debug < Information < Warning < Error < Critical`. Настройка `LogLevel:Default` задаёт минимальный уровень, начиная с которого сообщения попадают в вывод — при значении `Warning` логгер отбрасывает всё, что строго ниже него (`Trace`, `Debug`, `Information`), и пропускает `Warning`, `Error` и `Critical`, потому что они этот порог не ниже. Это позволяет в продакшене снижать «шум» от Information-сообщений, не теряя при этом сигналы о реальных проблемах.

## Контрольные вопросы

1. **Что такое Dependency Injection?** — паттерн, при котором зависимости передаются объекту извне (обычно через конструктор), а не создаются им самим; в ASP.NET Core этим занимается встроенный DI-контейнер.
2. **Какую проблему создаёт использование `new ProductService()` непосредственно в контроллере?** — контроллер жёстко привязывается к конкретной реализации: её нельзя подменить (например, моком в тестах) без изменения кода контроллера, а жизненный цикл объекта не управляется фреймворком.
3. **Для чего нужен интерфейс `IProductService`?** — отделяет контракт (что сервис умеет) от реализации (как это устроено), позволяя подменять реализацию и упрощая тестирование через заглушки.
4. **Что такое Constructor Injection?** — передача зависимостей через параметры конструктора; DI-контейнер сам создаёт и подставляет нужные реализации при создании объекта.
5. **Зачем регистрировать сервис в `Program.cs`?** — без регистрации DI-контейнер не знает, какую реализацию подставлять для интерфейса, и не может создать контроллер, зависящий от него (см. шаг 6 методички).
6. **Что делает `AddScoped`?** — регистрирует сервис так, что в рамках одного HTTP-запроса используется один и тот же экземпляр, а для каждого нового запроса создаётся новый.
7. **Для чего используется `ILogger<T>`?** — встроенный механизм структурированного логирования; `T` задаёт категорию сообщений (обычно класс-источник), что упрощает фильтрацию и настройку уровней.
8. **В чём разница между Information, Warning и Error?** — Information — штатное событие в работе приложения; Warning — потенциальная проблема, не мешающая выполнению запроса; Error — произошла ошибка при обработке запроса.
9. **Для чего используется `appsettings.json`?** — файл конфигурации приложения (в том числе уровней логирования, строк подключения и т. д.), позволяющий менять поведение без перекомпиляции кода.
10. **Почему слабосвязанный код проще изменять и тестировать?** — компоненты зависят от абстракций, а не друг от друга напрямую, поэтому одну реализацию можно заменить другой (или моком в тестах), не затрагивая остальной код.
